# Интересы компаний с учётом экономического окружения

Обогащение использует все три исходных CSV и сохраняет прежние собственные темы каждой компании. Результат — список интересов для каждой исходной записи, ссылки на конкретные связи и объяснение, почему деятельность связанной компании может быть значима.

## Какие связи установлены

| Вид связи | Что наблюдается | Как используется |
|---|---|---|
| Исходящий платёж | Компания платит контрагенту | Темы цен, доступности, качества и устойчивости деятельности получателя; роль поставщика/подрядчика — гипотеза |
| Входящий платёж | Контрагент платит компании | Темы спроса, загрузки и устойчивости деятельности плательщика; роль покупателя/заказчика — гипотеза |
| Общий человек | Совпадает `SYNTHETIC_F` | Дополнительный контекст деятельности другой компании; должность, владение и контроль неизвестны |
| Общая группа | Совпадает непустой `GROUP_ID` | Слабый контекст окружения; общие обязательства и юридическая структура не установлены |

Каждая связь содержит конкретные ID обеих компаний, точный ОКВЭД и деятельность контрагента, наблюдаемый тип связи, возможную роль, объяснение интереса и исходные основания. Платёжные связи дополнительно содержат агрегированную сумму, количество, направление, долю в сумме и количестве платежей соответствующего направления. Связи через человека/группу содержат общий идентификатор и размер окружения.

## Как выбраны интересы

Три субагента независимо подготовили интерпретации связей, выбор отраслевых аспектов и аудит данных. После этого субагенты подготовили тесты и независимый проверяющий скрипт. Обработка всех компаний выполняется кодом на основе этих правил, без отдельного LLM-вызова на каждый ID.

1. Все исходные платёжные строки проверяются. Платежи самой себе исключаются, повторные направленные пары агрегируются с точной арифметикой `Decimal`.
2. Для каждой компании отдельно считаются все исходящие и все входящие суммы и количества. Неизвестные контрагенты остаются в знаменателях. Доля — доля **наблюдаемых платежей**, не выручки, расходов или реального рынка.
3. Для переноса тем выбираются два наиболее значимых контрагента с достоверным профилем на каждое направление. Ранг равен `0.75 × доля суммы + 0.25 × доля количества`. Он описывает значимость связи внутри предоставленной выгрузки, а не вероятность или финансовый эффект. Самый значимый контрагент без профиля может не попасть в темы; его сумма остаётся в общей картине.
4. До двух компаний выбираются через общего человека и до двух через общий `GROUP_ID`. Представители крупнейших кластеров точного ОКВЭД показывают часть отраслевого окружения. Это ограниченная выборка представителей, а не полный список или рейтинг экономической значимости участников группы. При равенстве используется стабильный порядок ID. Сигналы ослабляются с ростом размера окружения.
5. По каждой выбранной связи переносятся четыре **отраслевые** темы точного вида деятельности контрагента. Правила выбора направления находятся в `relation_aspect_selection.json`; правила словесного объяснения — в `relation_policy.json`. Для узких overrides основного справочника берутся первые четыре специфические темы. Банковские продукты контрагента на компанию не переносятся.
6. Собственные темы сохраняются. Повторный ID темы не создаётся: к нему добавляются основания связей. Поэтому связь может дать новое объяснение уже существующей темы, не увеличив количество тем.

Приоритеты в назначениях: собственные темы имеют вес 1; платежи — `0.6 + 0.4 × ранг`; общий человек — `0.25 / sqrt(число связанных с человеком компаний − 1)`; группа — `0.1 / sqrt(размер группы − 1)`. Это эвристики для последующего ранжирования, не измеренная точность или доказанное влияние.

Точный ОКВЭД контрагента задаёт отраслевой контекст, но не доказывает предмет конкретного платежа. Для совпадения новости нужны и тема события, и контекст деятельности. Само наличие платежа не подтверждает покупку товара: возможны займы, возвраты, внутригрупповые и иные расчёты.

## Покрытие и ограничения источника

Аудит: 85 525 исходных профилей, 85 514 уникальных компаний; 1 380 585 платёжных строк; 12 514 связей человек–компания. В платёжной таблице 114 552 участника не имеют профиля в таблице компаний. Для них нельзя достоверно определить отрасль из этих данных. Платёжные назначения, период и валюта не предоставлены.

Один ID (`U_428697`) имеет 12 конфликтующих профилей. Его исходные записи и собственные интересы сохранены отдельно. Такой ID исключён как источник отраслевых интересов для других компаний; его платежи остаются в знаменателях.

Отсутствие выбранных связей не означает отсутствие поставщиков, покупателей или интересов. Для такой компании сохраняются все прежние 12+ собственных тем и явный статус отсутствия пригодного контекста связей. Полнота выгрузки не доказывает семантическую точность; потребуется оценка на размеченных парах компания/новость.

## Выходные файлы

Каталог `output/relationship_interests/`:

- `company_interests_enriched.csv` — по одной строке исходного профиля: собственные и добавленные темы с названиями, ID связей и итоговые количества.
- `company_interests_enriched.jsonl` — назначения тем, основания через ID связей, веса, собственный ОКВЭД, сводные платёжные показатели и статус. Идентификаторы исходных записей сохранены.
- `relationships.csv` и `.jsonl` — выбранные связи с подробными объяснениями, ролями-гипотезами, точными показателями и темами. Соединяются с профилем через `source_record_id`/`relationship_id`.
- `interest_catalog.jsonl` — полный использованный словарь тем `ci_` с отраслевым контекстом и объяснением аспекта; прежний каталог 10 000 тем `bt_` не подменяется.
- `payment_graph.sqlite` — все агрегированные направленные платёжные пары после исключения self-платежей, включая неизвестных участников. Таблица `payments`: `payer`, `beneficiary`, `amount` (точная десятичная строка), `payment_count`, `source_rows`.
- `relationship_examples.json` — примеры объяснений четырёх видов связи.
- `validation.json` — показатели поколения, ограничения, хеши исходных данных и правил.
- `verify_report.json` — результат независимой сверки всех назначений и выбранных связей с исходными данными.

CSV имеет UTF-8 BOM; массивы и объекты в ячейках закодированы JSON. Для программной обработки предпочтительны JSONL и нормализованный словарь.

## Воспроизведение

Из корня `Alfa-Hackaton`, Python 3.10+, только стандартная библиотека:

```bash
python3 taxonomy/enrich_relationship_interests.py --source-dir ../data/dataset
python3 taxonomy/verify_relationship_interests.py --source-dir ../data/dataset
python3 -m unittest discover -s taxonomy -v
```

Первый запуск требует уже созданного `output/company_interests/`. При необходимости он создаётся командой из `COMPANY_INTERESTS.md`. Повторный запуск перезаписывает только производные результаты текущего обогащения. Схема и данные исходных CSV не изменяются.

## Итог полного прогона

Сохранены все 85 525 исходных записей (85 514 уникальных ID). У каждой 12–50 различных тем. Выбрано 295 322 связи: 82 522 исходящих платежных, 72 562 входящих платежных, 655 через общего человека, 139 583 через общий GROUP_ID. Новые темы окружения добавлены 84 756 записям; всего добавлено 959 941 назначение сверх 1 229 802 собственных. Для 250 записей пригодных связей с известным однозначным профилем не найдено — собственные темы сохранены.

После исключения self-платежей полный граф содержит 1 353 162 направленные пары. Результат независимой сверки — в `verify_report.json`.
