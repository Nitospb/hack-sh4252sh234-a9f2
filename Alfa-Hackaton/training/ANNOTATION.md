# Проверенная связь объекта и новости

Сейчас ручных меток нет. `annotation/tasks.jsonl` — очередь проверки,
а не обучающий CSV. Автоматические баллы и suggested_evidence даны только
как подсказки; reviewer должен прочитать текст, при необходимости источник.
Можно добавить пару вне очереди, используя существующие family_key и ID
представителя из corpus/stories.jsonl. Отсутствие кандидата не означает
нерелевантность, а очередь не обеспечивает равное покрытие всех 1 000 объектов.

## Схема оценки

- `2`: статья существенно касается именно объекта/процесса, полезного для
  соответствующего интереса. В заголовке/тексте есть прямое доказательство.
- `1`: касается отрасли, но прямой связи с узким объектом нет. Сохраняется
  отдельно; не становится автоматически ни positive, ни negative.
- `0`: проверено, что статья не релевантна конкретному объекту, в том числе
  омоним/случайное упоминание. Это явный ручной negative.
- `null` или не approved: неизвестно; не используется в обучении.

Например, новость о банковской ставке не является автоматически новостью
о банковской гарантии. Новости о металлургии не подтверждают событие для
каждого продукта металлопроката. Не следует утверждать «рост/падение» по
названию группы или одной общей тематической связи.

Каждый готовый объект JSONL должен содержать:

```json
{
  "family_key": "существующий family_key из taxonomy/object_families.json",
  "article_id": "существующий ID представителя истории",
  "judgment": 2,
  "review_status": "approved",
  "annotator": "идентификатор проверившего человека",
  "reviewed_at": "2026-10-25T12:00:00+00:00",
  "reason": "почему именно этот объект связан с новостью",
  "evidence": "дословный непрерывный фрагмент заголовка или текста"
}
```

Это пример схемы, не настоящая размеченная запись. Для 2 нужен дословный
фрагмент >=8 символов; для 0 обязательна содержательная причина, evidence
можно оставить пустым. review timestamp должен иметь часовой пояс.
Дубликаты одной пары, неизвестные IDs, bool вместо оценки, отсутствие автора,
pending и несуществующие цитаты отвергаются. `prepare.py` проверяет структуру,
но не может удостоверить честность личности annotator или качество решения;
не создавай фиктивных reviewer и не выдавай ИИ-оценки за ручные.

## План разметки

Выбирай темы и положительные/сложные отрицательные статьи в каждой временной
части независимо. Для train нужны хотя бы positive=2 и negative=0 для одного
объекта; для val/test — тоже положительные и отрицательные пары. Код требует
непустых независимых holdouts и хотя бы двух готовых троек в каждой части,
но это технический минимум, не рекомендация по достаточному объёму. Для
качества нужны существенно больше тем/примеров и двойная проверка спорных пар.

Сложные negative ищи среди похожих по отрасли текстов, но различай их с
классом 1: один отраслевой контекст сам по себе не даёт проверенное 0.
Вноси неопределённые случаи в дополнительный журнал, не угадывай метку.
Тематические/источниковые пропорции и покрытие компаний проверяются отдельно.

Готовые оценки сохрани вне frozen bundle, например
`training/labels/reviewed-v1.jsonl` (игнорируется Git), и создай news-v2:

```bash
python -m training.prepare --labels training/labels/reviewed-v1.jsonl \
  --output training/data/news-v2
```

Сравни group_id и границы с news-v1: исходный набор тот же, разметка их не
меняет. В копии supervised config укажи data_dir новой версии. `prepare.py`
создаёт тройки только из ручных 2/0 той же темы и того же split. Для каждого
positive выбирается один детерминированный negative из одобренных; остальные
проверенные пары сохраняются в qrels для оценки. Ничего не домечается автоматически.

Метрики supervised evaluation — по проверенному пулу кандидатов каждой темы.
Они не являются recall по всему корпусу. Отдельно оцени перенос на темы,
источники и компании вне привычной выборки и точность автоматического допуска.

Положительный обучающий passage включает окно вокруг проверенного evidence,
даже если оно находится далеко от начала статьи. При оценке evidence не
используется для выбора текста: код считает все окна документа (256 токенов,
перекрытие 32) и берёт максимальное сходство, как основной каталог.
