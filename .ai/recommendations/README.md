# Лента рекомендаций

Локальное ядро и HTTP API поверх `pipeline/output/catalog.sqlite` и
производного тематического слоя `pipeline/output/ranking.sqlite`.
Исходный каталог открыт read-only; просмотры, реакции, интересы пользователя и
история выдачи сохраняются в отдельной SQLite `state.sqlite`.

Текущий общий запуск — [pipeline/README.md](../pipeline/README.md): новый
`pipeline/output/catalog.sqlite` автоматически выбирается при наличии,
веб-лента `/feed` подключена через `/api/live/`.
HTTP API и веб по умолчанию используют `mode=ranked`; `mode=strict` сохраняет
строгую проверку тематических назначений. Прямой Python API по умолчанию strict
для совместимости; передавайте mode явно.

## Запуск

Из корня репозитория:

```bash
python3 recommendations/server.py --port 8091
```

Для MMR используются уже рассчитанные E5 эмбеддинги: среднее чанков новости,
повторная L2-нормализация, cosine similarity. Нужен NumPy из окружения news_matching.
Без NumPy/эмбеддингов: `--no-embeddings`; сходство тогда по темам и словам заголовка.

```bash
curl 'http://127.0.0.1:8091/feed?company_id=U_1&user_id=demo&limit=20&request_id=page-1'
curl -X POST http://127.0.0.1:8091/events -H 'Content-Type: application/json' \
  -d '{"company_id":"U_1","user_id":"demo","article_id":"ARTICLE_ID","kind":"view","event_id":"unique-event-1"}'
curl -X POST http://127.0.0.1:8091/profile -H 'Content-Type: application/json' \
  -d '{"company_id":"U_1","user_id":"demo","topic_ids":["bt_00001"]}'
```

Вместо примеров article_id/topic_ids используйте реальные ID каталога.
Конфликтующие записи компании требуют `source_record_id` в GET.
Для следующей страницы используйте новый request_id; старый вернёт ту же выдачу.
Передача limit/source_record_id с уже использованным request_id не пересчитывает ответ.

## Ранжирование и обратная связь

Смешиваем нормированные признаки: 60% связь с компанией, 10% общие бизнес-темы,
10% популярность за 7 дней, 20% личные интересы. Это веса оценки, а не гарантированные
квоты слотов. Для компании различаем declared_activity (1), кандидат специализации
(.65), внешнюю экспозицию (.35); объяснение содержит реальный тип связи.
Свежесть плавно снижает score; будущие публикации исключены.
Общие темы определяются прозрачным правилом по названиям тем; ручная редакционная
подборка станет более качественной заменой этому правилу.

MMR = .75 × score − .25 × максимальное сходство с уже выбранными новостями,
плюс штраф за повтор источника. Одинаковый text_hash и почти одинаковые новости
не попадают в одну страницу. Семантические дубликаты определяются порогом .94,
который ещё нужно калибровать на разметке. Разные публикации одного события могут
остаться: полноценный межстраничный event clustering пока не реализован.

`view`, `open`, `like`, `save`, `dislike`, `hide` — события клиента.
Выдача сохраняет impression, но не создаёт view. Клиент должен посылать view,
когда карточка видна на 50% в течение 1 секунды в активной вкладке; это уже
реализовано через IntersectionObserver. Одинаковый event_id идемпотентен, конфликт payload отклоняется.
Просмотр/open исключает статью на 7 дней; активные реакции исключают её из
следующих подборок. unlike/unsave/unhide/undislike отменяют соответствующую
реакцию. Для каждой группы используется последнее действие, а не сумма кликов.
Impression резервирует статью этому пользователю в компании на 30 минут.
Это позволяет листать без повторов и вернуть пропущенные карточки позже.
Положительные и отрицательные сигналы меняют интерес к темам с затуханием 30 дней.
Повторы одного типа сигнала по статье не накапливают предпочтение; популярность
считает уникальные пары компания/пользователь. Профили пользователей изолированы
по компании, популярность общая. Роль сотрудника и topic_ids задаёт пользователь
в настройках. Должности из исходных таблиц не определяются.

## Реальные ограничения данных

Числа текущего корпуса и допусков вычисляются из `/health` и
`pipeline/output/ranking_report.json`. Сервис возвращает shortfall вместо искусственного
заполнения. Object/family назначения поддерживаются отдельно от событийных тем;
они не доказывают рост, падение или другое событие. `scope=strict` оставляет
прямую деятельность; `activity` добавляет кандидатов специализации, `interest`
добавляет косвенные интересы. `include_review=true` явно включает помеченные
кандидаты, сохраняя ограничения даты, текста и точных дублей. Нужна калибровка
порогов на размеченной выборке, точность пока не измерена.

Рекомендательный профиль дополняется 22 существующими операционными темами,
явно обозначенными гипотезами. Это не 22 подтверждённые специализации.
Существующие 10 000 тем не генерируются заново. Широкий отраслевой контекст
строится из E5-векторов и предметных якорей; налоговая госпрограмма не означает
разработку ПО. Подробности: `../pipeline/RANKING_ENRICHMENT.md`.

Витрина содержит пять реальных профилей разных отраслей. Проверка с реальными
эмбеддингами: по 24 + 24 новости без повторов; роли и отдельный просмотр меняют
персональный компонент. Отчёт `../pipeline/output/feed_acceptance.json`.
Это функциональная проверка, не измерение precision. Конечный корпус нельзя
бесконечно пополнять без нового сбора; после просмотров выдача может сокращаться.

HTTP сервер предназначен для локального прототипа, слушает только 127.0.0.1.
Перед эксплуатацией нужны аутентификация и проверка доступа к компании, миграции,
retention истории, лимиты запросов. Одновременные независимые запросы в прямом
Python API не резервируют страницы атомарно; локальный HTTP сервер обрабатывает
их последовательно. Рабочая веб-лента подключена, прочие экраны прототипа
сохраняют явно обозначенные демоданные.

## Проверка

```bash
python3 -m unittest discover -s recommendations -v
```

Тесты на синтетическом каталоге проверяют историю, повтор запросов и событий,
изоляцию пользователей, качество/даты и проверку пользовательских тем.
