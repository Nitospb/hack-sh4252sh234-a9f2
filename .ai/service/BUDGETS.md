# Доступность анализа и резерв проверки

`health.analysis_availability` — единый статус новых разборов, без платного
вызова шлюза. `llm_available` соответствует available, а не только наличию ключа.
Поля: available, reason, message, resets_at (ISO UTC либо null), policy.
Причины: missing_key, calls, tokens, gateway_budget, reserved, configuration,
ledger. В статус не попадают ключи, суммы usage, чужие runs или глобальные счётчики.

Локальный суточный день UTC сбрасывается в00:00UTC, то есть03:00МСК. Исчерпание
локальных вызовов/токенов или зафиксированная ошибка общего бюджета блокируют
новые задачи до сброса. Временный резерв текущих задач возвращает reserved:
можно дождаться их завершения, не обязательно следующего дня. О доступности
общего командного бюджета сервис узнаёт только от шлюза; расход других процессов
локальный ledger не видит. Присутствие ключа не доказывает его валидность.

## Приём задачи

Новый run допускается только при наличии ресурса хотя бы на draft+verify:
2вызова и консервативный резерв30000токенов на каждый. Проверка и запись
job_budgets выполняются в одной BEGIN IMMEDIATE транзакции с созданием runs.
Поэтому параллельный submit не занимает уже обещанную проверку чужой задачи.
При отсутствии ресурса ответ503 приходит до очереди/платного вызова, без
пустого failed-run. Уже завершённый cached-run возвращается даже при лимите.

Перед paid-вызовом один кредит job_budgets заменяется записью calls.reserved;
actual usage заменяет оценку по завершении. Резерв30000 — инженерная оценка,
не точный верхний предел размера ответа или денежный тариф. Локальный лимит
не гарантирует точной суммы счёта шлюза. Успешный ответ без total_tokens тоже
считается неизвестным расходом; negative/noninteger usage блокирует анализ
до исправления ledger. Не обнулять записи ради обхода лимита.

Оставшиеся кредиты освобождаются при любом завершении задачи; незапущенный job
также освобождает резерв. При безопасном перезапуске API незавершённые run/call
помечаются interrupted, будущие job-кредиты освобождаются, неизвестные уже
отправленные расходы учитываются до сброса. Рестарт выполняется только после
проверки отсутствия активных задач либо по отдельной операторской команде.

## Дополнительные шаги

Для contract repair заранее нужен резерв и на исправление, и на его verifier.
Если ресурса нет, лишний draft не отправляется. Непроверенный ответ не публикуется.
Для retrieve/revise резервируются ещё2вызова атомарно. Если ресурса нет, остаётся
первый проверенный черновик: per-claim gates сохраняют поддержанные выводы и
исключают неподдержанные, с явным ограничением дополнительной проверки.
Это не отменяет quote/fact/schema/date gates и не повышает candidate до confirmed.
Общие bounds двух draft/двух verifier и запрет transport retries сохранены.

## Интерфейс и проверка

При недоступном анализе показаны причина и дата сброса в МСК. Health обновляется
раз в30сек видимой вкладки, при focus/возврате и после завершения/ошибки анализа.
Кнопки платного анализа отключены. Лента, исходники, профиль, история и калькулятор
доступны; калькулятор показывается для выбранной новости и без готового LLM-run.

Тесты: service/tests/test_budget.py (резерв, гонка двух submit, cached answer,
UTC reset, unknown usage, gateway block, отказ запуска/repair, сохранение
проверенного ответа при невозможности refinement) и HTTP-проверки в test_http.
Никакие реальные LLM-вызовы для этой проверки не нужны.
