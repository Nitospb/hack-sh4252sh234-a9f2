# Условные механизмы влияния и уточнения (grounded-agent-v9)

В `service/planning.py` находятся восемь проверяемых групп механизмов: стоимость
финансирования, ВЭД, спрос/цены, налоги, логистика, персонал, киберриски, технологии.
Это детерминированные правила, не обученная или свободно планирующая LLM.

Для найденных в заголовке/начале текста механизмов план хранит:
company_fact_ids → transmission_hypothesis → условия/ограничения → вопросы.
Флаг1 разрешает проверить соответствующий канал. Нулевой флаг или candidate
не становится подтверждённой экспозицией. Гипотезы всегда conditional; суммы,
валюты, ставки и сроки из флагов не появляются. Неизвестные единицы выручки и
рыночный знаменатель остаются unknown.

Роль меняет приоритет механизмов: казначей начинает с финансирования/ВЭД,
бухгалтер с налогов, IT с киберрисков/технологий. Из нескольких механизмов сначала
выбирается по одному вопросу; пользователю предлагается не более трёх приоритетных
уточнений. Текст вопроса уточняет фокус, но не добавляет подтверждённый факт.

Вопрос «какие параметры уточнить» выбирает context → draft → verify; первичный
bank search пропускается с явной trace-записью. При запросе позиции/прогноза банка
поиск сохраняется. Verifier по-прежнему может запросить дополнительные основания.
Сгенерированный вывод проходит прежние schema/source/date/quote/verification gates.
План передаётся генератору как гипотеза, не первоисточник события.

Ранжирование `ranked-v4-observed-relationships`: до8 наблюдаемых связей с приоритетом
входящих/исходящих платежей соединяются с прямой отраслью контрагента. Сигнал
ограничен .06 для платежа или .025 для общей группы/лица, внутри company-компоненты.
В выдаче сохраняются relationship_id, source evidence и caveat. Это основание
для поиска применимости, не утверждение собственности, поставки, гарантии,
передачи риска или доли рынка. Строгие исходные topic labels не меняются.
Условия кредита/ВЭД по-прежнему требуют проверки. Assets version учитывается в
кэше; после переключения каталога используются прежние независимые assets.

Проверки: service/tests/test_planning.py, test_relationship_ranking.py,
существующие runtime/serving tests. Качественный выигрыш на независимом ручном
наборе пока не измерен. Более свободное планирование, расчёт сценариев с
подтверждёнными числами и обязательный экспертный эталон остаются в W02/W05.

## Версия v11: несколько публикаций и гибридный банк-поиск

Актуальное продолжение: [STORIES](../pipeline/STORIES.md). Дополнительные статьи
попадают в отдельные related_news с исходными IDs/версиями. Generator и verifier
видят их отдельно от PRIMARY_NEWS и банковских исследований. Exact quote и дата
проверяются для каждого источника. Модель не может выдать похожую публикацию за
независимое подтверждение или усреднить цифры разных показателей.

Банк-поиск объединяет FTS и смысловую близость к исходной новости: mean news E5
сравнивается с банковскими passages того же checkpoint. Это **event-semantic**
канал, а не отдельный semantic encoder вопроса пользователя. Уточняющий вопрос
влияет на лексический канал и план. Reciprocal rank fusion сохраняет оба сигнала;
не более2 passages/документ. Известная дата<=as_of, окно180дней, качество OCR,
text/document SHA и равенство encoder SHA обязательны. При отсутствии/несовместимости
semantic index остаётся FTS. Scores не являются вероятностями/экспертной оценкой.

Offline подготовка (ML-среда, только инференс, без optimizer/training):

```bash
python -m service.bank_embeddings --assets pipeline/output/service-assets.sqlite --output pipeline/output/bank-semantic.sqlite --backend mps
```

API читает маленький SQLite рядом с неизменяемыми service-assets; Torch в online
образ не добавлен. При изменении OCR/PDF повторите подготовку; устаревшие passages
отбрасываются по SHA. При замене E5 checkpoint нужно пересчитать и news, и bank
vectors одинаковыми весами. CPU ONNX-векторы не смешиваются с Torch checkpoint.
Состояние канала отображается в health.bank_retrieval и на странице quality.
Hybrid retrieval добавляет кандидатов, но применимость позиции банка, периоды и
OCR-числа требуют содержательной проверки. Независимый retrieval benchmark пока
не размечен; семантические пороги не заявляются доказанной точностью.

## Версия v12: частичный полезный результат

`service/verification.py` разделяет event_verdict, bank_verdict и claim_reviews
для каждого why_for_company/ai_application/risk/opportunity/action. Общий verdict
управляет запросом дополнительного поиска/контекста; он больше не обнуляет
индивидуально поддержанные тезисы.

Каждый claim имеет request-local ID вида `actions/0`. Production verifier обязан
вернуть оценки всех пунктов по новой JSON Schema. Отсутствующая/дублированная
оценка не считается поддержкой. Локальный gate дополнительно требует известные
fact IDs, conditional для candidate фактов, точные цитаты каждого source ID и
подтверждённый первичный event. Неподтверждённая сумма/неусловный выдуманный договор
исключаются отдельно, без автоматического переписывания в будто бы истинный тезис.

Неизвестные остаток долга, индекс, валюта и срок ограничивают расчёт денежного
эффекта. Если условный канал и конкретное действие подтверждены источниками и
профилем, они остаются в needs_context. Сам status не является ошибкой исполнения.
Frontend показывает «Есть выводы — уточните детали» при непустом частичном ответе.
Вопросы к клиенту берутся из missing_context/context_questions, до3; технические
issues не подменяют их. Подтверждённая нерелевантность остаётся not_relevant.

Позиция банка проверяется отдельно как summary+relation+applicability+limitations:
неизвестный договор клиента не отменяет исходный датированный тезис. Bank claim
не сохраняется без своей оценки/цитат или если банку приписано неподтверждённое
мнение о конкретном клиенте. Personal claims со ссылкой на этот текст также
проверяются самостоятельно. Это автоматическая проверка, не экспертный gold.

В output.verification.publication и validate_output trace находятся kept/dropped,
решение по каждому claim_id, статус события/банка и число отброшенных цитат.
Старые сохранённые runs остаются без изменения; v12 инвалидирует serving cache
для новых анализов. Совместимость legacy_global оставлена только для старых
внедрённых offline verifier-функций в тестах/интеграциях; штатный LLM-путь требует
полную per-claim schema и не может обойти её, опустив claim_reviews.

Проверки: test_partial_verification.py (6 edge cases), runtime regression с
needs_context/поддержанным действием/ложным расчётом, существующие scope/quote/
source/date/contract tests. Числа, договоры, единицы выручки и рынок по-прежнему
не угадываются. Неопубликованные тезисы видны в scoped trace для разбора ошибок.

## Версия v13: оценка сначала, вопросы только при критическом пробеле

Уточнение пользователя: сервис сам даёт наиболее обоснованную оценку, вместо
того чтобы выдавать клиенту общий список проверок. Generator начинает с ai_application:
направление/качественный масштаб/основания/уверенность и явный базовый сценарий;
при необходимости — альтернативный. Неизвестные суммы/индексы/сроки не превращаются
в известные договоры. Денежные суммы, проценты вероятности, единицы выручки не
выдумываются. Клиент не должен перепроверять работу сервиса с открытыми источниками.

После независимой проверки достаточная полезная оценка с подтверждённым фактом
компании и точными цитатами может быть ready с оговорками, даже если отдельный
ложный расчёт удалён. Отдельный блок why не обязателен, если связь объясняется в
поддержанном AI/risk/action claim. Одних candidate фактов для ready недостаточно.
Генерирование ready по-прежнему не является независимой метрикой точности.

Verifier context_questions обозначает только критический пробел: без ответа
существенно меняется решение и нельзя дать полезную оценку даже через явно
указанные сценарии. Публикуется максимум1 такой вопрос. Необязательные черновые
вопросы не превращаются в обязательное действие клиента. Если пользователь сам
попросил список параметров/условий, запрошенный список (до3) сохраняется как ответ.

Дополнительный local guard: формулу «14% + спред» нельзя выдавать за ставку
компании без явно названной привязки договора к ключевой ставке. Просто «если
есть плавающий кредит» не задаёт benchmark. РКО/ЗПП не равны кредитной линии.
Сегодняшнее решение ЦБ не является гарантией траектории ставок до конца года.
Frontend сначала показывает оценку, затем детали/действия, затем публикации/цитаты.
